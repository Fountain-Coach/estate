# Recovery State Manifest — public metadata contract

**Authority:** [ADR 003 — Owner Continuity and Golden Key Recovery](../../docs/decisions/003-owner-continuity-golden-key-recovery.md).

This directory contains a **metadata-only** inventory of 16 classes that may matter for institutional continuity. It does NOT hold protected data, actual live Store instance identities, credentials, key material, registered successor credentials, or a private backup. Its explicit incompleteness is a safety property.

- [state-manifest.json](state-manifest.json) maps the known data classes, owner components and governance references, classifications, backup policy requirements, permissible recovery paths and current readiness.
- [readiness.json](readiness.json) is computed from the typed manifest and is intentionally NOT READY for owner continuity.
- [README.md](README.md) explains the six acceptance gates and their evidence deficit.

## Classification and authority

FCIS 118 requires three distinct data classifications:

1. Institutional knowledge can be exported under an approved purpose with exact provenance, eligibility and rights.
2. Personal context requires purpose limitation, consent/eligibility, omission, retention and erasure guarantees. A source record must not be made public simply because an agent has seen it.
3. Authority-bearing capability must **never enter the open recovery channel**. A native custody mechanism and genuinely approved owner recovery path are separate requirements.

The source-owner repositories in this manifest are **component ownership references**, not assertions that current operations have been enrolled, deployed or backed up. The FountainStore RecoveryKit can produce a typed projection from authority-supplied records but does not itself prove that a live Store has been exported. The public swift-secretstore library implements custody backends but does not supply missing production authorization. FountainAuthKit's tested library is not an asserted live identity provider.

## Golden Key

FCIS 139 documents a production owner trust root, a distinct local root, and an **absent accepted lost-root/break-glass operation**. That condition is pinned as BLOCKED in this contract. A different root, a new key, SSH root access, a password, or an LLM assertion must not establish operational or succession authority. FCIS 143 requires a single bounded owner bootstrap/session, with explicit new owner decisions for genuine changes of trust.

## Stage 1 acceptance

The deterministic validator MUST reject missing/duplicate state classes, unknown classification, open distribution of personal/authority material, unexpected credential fields, fake private evidence receipts, false accepted lost-root status, invalid production authorization, and propagation of the static 600/600 proof to a private recovery claim.

Run:
- npm run recovery:state:build — regenerate the deterministic readiness report from the manifest
- npm run recovery:state:verify — verify the report is fresh and the contract remains fail-closed
- npm run recovery:state:test — run the 18 synthetic positive/negative tests

These operations are local and read-only except for report generation. No automated remote backup, Store mutation, credential enumeration, DNS change, cloud integration or public deployment is performed.

## Stage 2 — authorized read-only operational inventory

The next authority-sensitive work must first select and identify legitimate production FountainStore instances and other operational custody classes through an **enrolled native adapter and bounded owner approval**. Before any operation:

- Identify the exact target trust root/host/service, permissions and intended scope *within the protected execution context*; no raw credentials or secret-bearing paths enter this public repository.
- Validate classification and exclusion policy before reading any records.
- Produce a **redacted, typed inventory receipt** with source authority class, schema/version, observed time and sequence watermark where appropriate, eligible and omitted category counts, the owner's classification authorization result, opaque evidence-reference digest, completion/refusal status and read-only attestation.
- Do not include Store record contents, personal identifiers, raw key bytes, device IDs, private paths, bearer tokens or actual backups in the public receipt. The protected receipt may remain private; the Estate receives only a separately authenticated minimal acceptance summary.
- A receipt generated by an arbitrary script or LLM does not satisfy native authority. Preserve the signed/typed source adapter terminal receipt and independent readback.
- Missing owner authority, stale trust, incomplete inventory, unsupported classification or protected-service unavailability => refuse and preserve BLOCKED state.

After Stage 2, separately design an encrypted off-host snapshot mechanism for eligible state and an independent clean-room restore proof under the owning component. Do not treat this metadata contract as permission to initiate that work.

## Stage 3–5 DoD

All six criteria in ADR 003 must pass: complete actual inventory; independently recoverable protected backups; lawful/legitimate Golden Key and successor authority; clean-room recovery; permitted publication continuity; and independently repeated, timed, owner-accepted receipts.

Cloudflare named tunnel/DNS management is explicitly deferred to the final availability milestone in ADR 002. The objective of the present programme is trustworthy private continuity, not rapidly switching production DNS.

No GitHub Actions or CI workflow is added. This contract belongs to Fountain-Coach/estate; actual source-specific implementation remains the responsibility of FountainStore, SecretStore, FountainAuthKit and enrolled host services.
