# Development, staging and production: production-first, Git-based lineage

**FCIS procedural application — 23 October 2026.** Read with `SKILL.md`, [FCIS reconciliation](fcis-authority-and-reconciliation.md), [the Invented-Prerequisite Loop](invented-prerequisite-loop.md), and the currently applicable Governance. Production-first staging is the author's *explicitly requested transition outcome*, not evidence that every historic publisher must be replaced or receive a new security subsystem. Scope is the selected canonical Git-to-staging promotion. A skill ZIP cannot supply missing native enforcement; neither may it disable an otherwise working SSH publication operation to force an invented mechanism.

## Three identities, not three public DNS zones

| Role | Grounded authority | Permitted effect | Not implied |
| --- | --- | --- | --- |
| Development | Each source-owning Git repository, branch and exact commit SHA; approved source/rights | Author/edit direct-static HTML/CSS/JS; native lease-bound local FountainStore preview and digest-bound check-in where applicable | A `dev.*` DNS endpoint, production revision, stage/public deployment |
| Staging | `Fountain-Coach/estate/staging/environment.json` plus *current* SSH symlink, existing Ubuntu Mac mini service, immutable stage release and typed receipt | Serve and proofread the authorized combined candidate on the owner WLAN; keep rollback | DNS production, another stage environment, automatic author approval |
| Production | Per-host public HTTPS/DNS/TLS bytes independently observed; owner release/Store receipts where available | Establish what is actually published at observation time, serve admitted release | Automatic ownership over Git, permission to rewrite authored source, assurance from one HTTP 200 |

Development can use the native `<canonical-host>.localhost:<managed-port>` FountainStore preview lease under current rules. Do **not** create `dev.fountain.coach`, a new public wildcard, a staging-to-production alias, a generic copied directory server, or an additional renderer merely to give development an address. A specific OAuth/secure-origin test may justify a separately scoped origin only when the existing preview is proved insufficient; do not generalize that exception.

## Decision by user goal

| Requested action | Production baseline required? | Allowed action |
| --- | --- | --- |
| Show/current staging, inspect why a page looks wrong | **No promotion precondition** | Read registry, inspect live `current`/service, return a copyable URL and observed content; no mutation |
| Edit Git; review native local FountainStore preview | **No** | Author source and verify local snapshot; no staging activation |
| Refresh staging to reproduce current production without development changes | **Yes for the selected material** | Capture complete observed production scope as immutable input and activate an approved production-only snapshot using existing owner operation; no Git overwrite |
| Promote a development delta into **canonical** staging with the author-requested production-first guarantee | **Yes, for affected scope** | Reuse observed production release evidence + explicit Git delta + staging predecessor; verify using existing publisher/SSH operations. Claim *guaranteed enforcement* only when the actual running client checks it |
| Public release after staging | **Distinct approval**, not inherited from stage | Apply current source/rights, artifact-only Chapter 148 and native public EstatePublisher authorization/readback |

A brand-new, explicitly authorized route with no public predecessor needs *independent evidence that no deployed predecessor exists* and a declared `new-route` delta. Do not synthesize a blank production baseline for a route that already exists. Report unavailable production evidence as unknown; do not treat network failure, a missing receipt or single 404 as proof of absence.

## Canonical development-to-staging sequence

1. **Fix scope and owners.** Record selected host/path set and asset dependencies, exact Git repository and 40-character SHA for each owner, intended `add / modify / delete / preserve` changes, rights, and explicit author intent. Don't treat latest `main` or a branch name as a release identity.
2. **Verify the selected production baseline.** Prefer an already accepted exact immutable production release inventory/receipt, then independently verify the relevant HTTPS bytes, routes and assets for the *affected scope*. If no reliable inventory exists, collect the missing bytes and digests read-only. Recheck changed/unavailable evidence, but do not demand an unrelated full-estate crawl for a single route. An index HTTP 200 or historical README is not evidence of complete selected-scope fidelity; production remains unchanged.
3. **Reuse or prepare an immutable, nonactive production baseline.** When the selected baseline already exists with independently verified SHA inventory, reference it rather than importing the same bytes again. Otherwise prepare it using the current working estate staging path. Preserve original production digests separately from stage-specific WLAN rewriting. Do not switch the author-facing `current` service to bare production as a ceremonial intermediate, and do not overwrite Git authoring.
4. **Apply exactly the declared Git delta off-line.** Project approved changes against that baseline; use domain-owned Git content, preserved assets and explicit stage-only link/hostname transformations. Create a separate candidate inventory and a route-aware diff: added / modified / deleted / preserved, with stage-only transforms identified. Explicitly reconcile existing accepted stage-only work so a refresh does not silently erase it. Unknown deletions, foreign owner changes, missing dependencies or rights gaps are refusals, not harmless file-count differences.
5. **Check the actual existing EstatePublisher contract.** Inspect its installed CLI/operation, stage profile and current source. For a *guaranteed* production-first transition the smallest sufficient native guard must correlate: the selected production baseline identity/digest, pinned Git source + declared delta, candidate inventory, expected staging predecessor and intended target. Recheck the relevant production bytes/release and current stage predecessor immediately before activation. Use the existing manifest/receipt shape where possible; do **not** demand a seven-field schema, newly invented authorization handshake, restricted deployment account, sidecar, SecretStore, host agent or replacement SSH transport unless a specific demonstrated constraint actually requires it. If the installed client cannot enforce the writer-requested guarantee, report **NOT YET GUARANTEED** and make a bounded correction in its existing delivery path. Do not reclassify unrelated ordinary static publication as blocked, or claim a manual preflight alone is machine enforcement.
6. **Activate one immutable candidate through the existing approved SSH delivery path and prove it.** Keep previous release rollback-ready. Independently read back the selected route/assets, actual stage service and symlink, and browser/AX only where the specific goal needs it. Persist the original-path release receipt. Hashing the copied candidate does not alone prove it correctly incorporated production. Do not install an extra server-side executor or invent a browser test matrix as acceptance.
7. **Report exact state.** Give the author the canonical stage URL from the registry/live host; source owner SHAs; observed production reference; delta and preserved content; candidate and active stage IDs; receipt; separately unverified defects. Do not declare a public deployment unless separately executed and independently witnessed.

A **stage predecessor check is not a production-baseline check**. The October 23 audit of `Fountain-Coach/EstatePublisher` PR #1 observed `previousReleaseID` in its `StaticReleaseManifest` and `deliver()` implementation, but no mandatory production-source/delta lineage admission. Re-evaluate current repository HEAD and native runtime before claiming the defect remains or has been fixed; never infer adoption from an open PR, a skill upload, or passing mocked tests.

## Focused acceptance cases for the *requested* guaranteed transition

- **No baseline:** reject a *claimed guaranteed* Git-to-stage candidate with no verified evidence of the relevant production scope; do not require a new remote receipt service where the existing release inventory and readback suffice.
- **Stale baseline:** reject if a relevant public route/asset or published release changes after baseline capture.
- **Partial baseline:** reject missing selected-scope dependencies or a one-page snapshot advertised as whole-estate equality; do not expand route-scoped verification into a mandatory estate-wide audit.
- **Unexpected content changes:** reject undeclared deletions, content replacement, foreign owner updates and disappearance of previously accepted stage-only work.
- **Git uncertainty:** reject unpinned/ref-mismatched Git SHAs and modified inputs after candidate manifest creation.
- **Stage race:** reject changed active staging predecessor between inspection and activation, preserving the running release.
- **Stage-only transform:** accept only explicitly declared WLAN link/host rewrites; do not confuse them with original production byte equality.
- **Failure and rollback:** preserve and verify the previously active stage release when stage inventory or independent readback fails; do not claim successful activation when rollback is unverified.
- **Negative target:** refuse public-domain target in a staging command and refuse use of the wrong Ubuntu preview service as the canonical staging entrance.
- **Positive path:** baseline independently observed; immutable source import evidenced; exact Git delta and preserved assets proven; production and stage both current; typed native promotion and stage readback correlate to one release identity.

These tests prove only their own exercised contract, not the necessity of unrelated machinery. Native verification of the requested guarantee is distinct from ordinary SSH publication. Preserve the existing authenticated SSH/rsync/SHA-256/atomic-symlink/rollback/readback path: neither a separate FCIS host agent nor a restricted SSH account, extra signing ceremony, Store replication, new DNS zone, browser matrix or GitHub CI is a default prerequisite. Apply the [Invented-Prerequisite Loop test](invented-prerequisite-loop.md) before broadening acceptance.
